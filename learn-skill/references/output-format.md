# Learn Skill Output Format

Use this format in the final answer after the coding task is complete. Keep it token efficient. Omit any section that does not apply.

## Default Format

**What changed**
- Name the changed file or area.
- State the behavior added, fixed, or refactored in one sentence.

**Why it was needed**
- Explain the problem or goal the change solves.
- Connect this directly to the user's request.

**How the code works**
- Explain the important functions, components, data structures, or commands.
- Use short bullets. Do not explain obvious syntax.
- Include a tiny code excerpt only when it makes the explanation clearer.

**Flow**
- Describe the runtime path in order.
- Start from the trigger or entry point.
- End at the visible result, returned value, saved state, or side effect.

**Things to notice**
- Mention validations, tests, edge cases, assumptions, or limitations.
- Keep this section to one to three bullets.

## Small Task Format

For very small changes, use this compressed form:

**Learn**
- `What`: one sentence about the change.
- `Why`: one sentence about the reason.
- `How`: one to three bullets explaining the logic or flow.

## Style Rules

- Be direct and concise.
- Prefer file/function names over vague labels.
- Use bullets instead of long paragraphs.
- Avoid generic programming lessons unless they are necessary for this exact code.
- Do not include unrelated implementation history.
